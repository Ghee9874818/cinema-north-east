## Safety and failure behavior

- Collectors run independently for Alnwick Playhouse, Tyneside Cinema and Everyman
  Newcastle. Each uses a new temporary candidate path and a 180-second timeout.
- No Vue network request is made. The known blocked Vue source and unimplemented
  ODEON/Cineworld sources retain their existing rows and statuses, with no invented
  attempt timestamps.
- Candidates must have the expected venue and live mode, a current-run timestamp,
  seven-day London-date coverage, official source URLs and content hashes. The
  existing merger additionally rejects empty, malformed, multi-venue, older,
  future, stale and out-of-coverage data.
- A failed candidate never replaces its venue. Last successful rows, collection
  timestamp and coverage survive; only failure status and actual attempt time
  change. Other venues still refresh. A fully failed run preserves every row.
- A missing, corrupt or unsupported-schema baseline stops before collection.
  One atomic file replacement publishes the final merged feed. Write failure
  leaves the original bytes intact.
- The workflow runs tests before collection and commits only `screenings.json`.
  Git pushes are non-force: a concurrent change to main rejects the update, and
  the dependent deployment never starts. A second main-SHA check before deployment
  rejects an artifact already superseded by another main update. Before this check,
  a read-only gate waits for earlier autogenerated Pages builds to become terminal;
  a workflow-file push must also have its legacy build registered. This prevents
  the initial old-data Jekyll build from completing after the fresh artifact. If
  that gate is not satisfied within five minutes, deployment stops.
- The native per-run GitHub token gets `contents: write` only in the refresh job.
  No credentials are persisted in checkout or git configuration. The deployment
  job has only `contents: read`, `actions: read`, `pages: write` and `id-token: write`.
- No account, repository security, Pages-source or environment setting is changed.
  Source-branch deployments are explicitly described in the official deploy-pages
  security guidance; this workflow originates only from existing source `main`.
  Existing environment restrictions are respected. Actual successful deployment
  is the activation gate; if denied, report the precise blocker rather than
  altering settings or adding another credential.
- The uploaded Pages artifact contains exactly `index.html` and `screenings.json`.
  Reports are separate run artifacts. `_config.yml` also excludes code, fixtures
  and review documentation from future legacy branch-based Jekyll builds.
- A native token's feed commit does not trigger another push workflow. Independently,
  this workflow's push filter excludes the feed path. There is no refresh loop.
- A successful deployment is checked against SHA-256 hashes of both public files,
  allowing up to five minutes for propagation. A mismatch remains a failed run.
  Future manual main changes can still race deployment because GitHub has no
  repository-wide deployment compare-and-swap; inspect or rerun if that happens.
